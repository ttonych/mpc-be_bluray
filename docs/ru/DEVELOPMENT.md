## Структура и версии

Исходники MPC-BE и история оригинального Git-репозитория находятся в корне.
В `bluray` размещены сборочные скрипты интеграции, проверки, локальные патчи и
[закреплённые версии](../../bluray/versions.json). Загруженные исходники libbluray
и сборочные зависимости исключены из Git. Отдельного репозитория-форка libbluray
на этом этапе нет.
Порт vcpkg в `bluray/ports/libudfread` использует официальный архив VideoLAN 1.2.0
и опубликованную SHA-512: вместо генерируемого архива GitLab может прийти HTML
с проверкой на бота. Сохранён MSVC-патч закреплённого порта vcpkg; версия
библиотеки не меняется. Лицензия MIT порта — в `bluray/ports/LICENSE.txt`;
в комплект плеера она включается как `licenses/vcpkg-port.txt`.
Возвращаться к отдельному репозиторию библиотеки имеет смысл, если эти изменения
понадобятся другому плееру, например будущей интеграции с MPC-HC.

Текущая основа — официальный **1.9.1**, commit
`d2c7b28a22ffe5ddd72632c9076d594ac6d2178f`. Первый выпуск форка планируется как
`1.9.1-bluray.1`; следующий на той же основе — `1.9.1-bluray.2`, а при переходе
на новую основу счётчик начинается заново, например `1.9.2-bluray.1`.
В локальном плеере версия продукта пока отображается как `1.9.1`; номер форка
записан в имени пакета и манифесте. Оформление версии в интерфейсе ещё предстоит закончить.
Имя репозитория — `mpc-be_bluray`; планируемое название в интерфейсе — **MPC-BE
Blu-ray**, с указанием, что это неофициальная модификация. Прежняя база `1.9.1 dev`
заменена официальным релизом, поэтому в номере готовящегося выпуска нет `dev`.

`main` предназначена для проверенного кода; изменения ведутся в коротких ветках
`feature/`, `fix/` и `update/`. Постоянная ветка develop не нужна. Исходники уже
опубликованы; первый выпуск для скачивания ещё готовится.

## Ветки и порядок выпуска

Работайте локально в подходящей короткой ветке, выполните необходимые тесты,
затем отправьте подготовленные изменения через PR. Перед слиянием в `main`
проверьте diff и успешные проверки; после слияния удалите завершённую ветку.
Защита `main` требует PR и успешной проверки `source-check`, в том числе для
администраторов. Принудительная отправка и удаление ветки запрещены.
Одобрение вторым человеком не требуется.

Порядок выпуска:

1. Локальная разработка и тесты, проверка PR, слияние в `main`.
2. Ручной запуск полной сборки Actions для выбранного commit в `main` теми же
   сборочными скриптами, которые используются локально.
3. Создание черновика Release для этого commit с полученными ZIP, SHA-256,
   версиями компонентов и описанием изменений на русском и английском.
   До окончания проверки выпуск остаётся черновиком и не публикуется.
4. Проверка именно облачного ZIP с madVR, HDMV, BD-J и чистым портативным профилем.
5. Публикация того же ZIP и контрольной суммы с соответствующим тегом исходников.
   Не пересобирайте и не заменяйте файлы после проверки; любое изменение требует
   повторной проверки кандидата.

Текущий workflow только загружает артефакты Actions. Создание черновика и публикация —
отдельные шаги выпуска; workflow сборки их не автоматизирует.
Скачайте и сохраните ZIP и контрольную сумму до истечения 14 дней хранения
артефактов. Публичные выпуски используют облачную сборку; локальные
пакеты служат для разработки и диагностики.

## Локальная сборка

Потребуются:

- Windows x64, Git, PowerShell 7 (`pwsh`), Python 3.13 и `7z` в PATH.
- Visual Studio 2022 с разработкой классических приложений C++, MSVC v143,
  ATL/MFC и Windows SDK `10.0.19041.0` либо явно заданным установленным SDK.
- JDK 21 с `bin/javac.exe` для компиляции Java-классов libbluray. Для просмотра
  достаточно JRE из [руководства](USAGE.md#java-для-bd-j).

Клонируйте этот форк по его адресу GitHub. Команды ниже выполняются из корня
репозитория. В `$jdkRoot` укажите свою папку JDK; путь в примере условный.

```powershell
git submodule update --init --recursive
git config core.hooksPath .githooks
$jdkRoot = 'C:\Java\jdk-21'
./bluray/tools/prepare-dependencies.ps1
./bluray/tools/build-libbluray.ps1 -DependencyRoot "$PWD/bluray/build/vcpkg_installed/x64-windows"
./bluray/tools/build-bdj.ps1 -JavaHome $jdkRoot
./bluray/tools/test-components.ps1 -JavaHome $jdkRoot
./bluray/tools/build-player.ps1
```

Подготовка зависимостей загружает закреплённый GCC/MSYS для MPC-BE и собирает
манифест vcpkg на закреплённой ревизии. Существующая копия vcpkg другой версии
отклоняется. Для архивов libbluray и Ant проверяются контрольные суммы.
Версии Python-пакетов указаны в
[requirements-build.txt](../../bluray/tools/requirements-build.txt).
Оригинальная [инструкция сборки MPC-BE](../Compilation.txt) сохранена для справки;
для этого форка используются команды выше.

`build-player.ps1` принимает `-SdkVersion`, `-ToolchainRoot` и `-RuntimeDirectory`.
Готовый инструментарий можно указать через `MPCBE_MSYS`. Это локальные настройки:
файл окружения с путями конкретного компьютера не должен попадать в Git.

| Результат | Расположение |
| --- | --- |
| DLL libbluray, JAR и диагностические программы | `bluray/out/libbluray-1.5.0-x64` |
| Плеер и русская DLL ресурсов | `bluray/out/mpc-be-bluray-x64` |
| Журнал сборки плеера | `bluray/diagnostics/logs/player-build.log` |
| Промежуточные файлы и символы плеера | `_bin` |
| Результаты тестов и тестовые данные | `bluray/build` и `bluray/diagnostics` |

Сборка сохраняет существующий INI плеера. По умолчанию используется
`BlurayPortableTest=true`: отдельный INI и импорт при первом запуске.
`build-player.ps1 -StandardProfile` возвращает штатную политику профиля MPC-BE
для будущего обычного выпуска; упаковщик портативной тестовой версии этот режим
отклоняет. Для первого публичного тестового комплекта он не используется.

## Проверки и упаковка

`test-components.ps1` запускает искусственные C++-проверки, регрессионные тесты
обоих патчей, HAVi-тесты собранного JAR и тесты проверки публикации. Диск не нужен.
Отдельные сценарии: `test-mouse-submenus.ps1 -Disc 'V:\'` для Baby Boom и
`test-menu-background.ps1 -KingdomDisc 'V:\'` для The Kingdom. Они требуют
соответствующего диска и не являются универсальными валидаторами.
`test-hdmv.ps1 -Disc 'V:\'` проверяет HDMV-навигацию. Журналы и тестовые данные
остаются локально.

Живые проверки выполняются с **madVR**, под который адаптирована интеграция.
Нужны диски HDMV и BD-J: вступление и неподвижные изображения, выбор меню, запуск
фильма, выбор дорожек, главное/всплывающее меню, главы, масштаб окна и смена диска.
При изменении интерфейса или импорта проверяйте чистый портативный профиль и
оба языка. Компонентные тесты не подтверждают видимое изображение, звук и HDR.

Для публичного кандидата проверьте и закоммитьте исходники, пересоберите и упакуйте:

```powershell
python bluray/tools/check-public-tree.py
python bluray/tools/package-player.py
```

Для локальных экспериментов `package-player.py --allow-dirty` принимает сборку
с незакоммиченными изменениями и добавляет `-local` к имени. Архивы создаются
в `bluray/out/packages`; существующий архив не перезаписывается. Упаковщик
проверяет хеши программ, использует явный список файлов и создаёт чистый INI.
Java, madVR, личные профили, данные дисков, журналы и символы отладки исключены.

Текущий упаковщик кандидата ещё не включает эти новые пользовательские документы.
Перед первым публичным выпуском нужно подключить итоговые двуязычные инструкции
к ZIP. Существующий локальный кандидат не является готовым публичным выпуском.

## GitHub Actions

- [Быстрые проверки](../../.github/workflows/bluray-checks.yml) запускаются для PR
  или вручную: проверяют материалы публикации и сам сканер, ссылки/примеры нашей
  документации, идентификаторы RU/EN-строк, аргументы форматирования и элементы
  наших диалогов. Качество перевода и размещение элементов проверяются отдельно.
  Локальный запуск проверки документации и ресурсов:
  `python bluray/tools/check-docs-and-resources.py`.
- [Полная сборка](../../.github/workflows/bluray-build.yml) запускается только
  вручную на `windows-2022`: libbluray, Java-компоненты, тесты, MPC-BE и русские
  ресурсы, затем ZIP и контрольная сумма.
- Обычный push не запускает полную сборку. Разработка и эксперименты идут локально;
  облачный кандидат выпуска собирается после слияния проверенных изменений в `main`.
- Workflow имеет права чтения репозитория и не публикует GitHub Release.
  Артефакты хранятся 14 дней.

Actions закреплены по commit; загрузки зависимостей, baseline vcpkg и версии
инструментов закреплены отдельно. Побитовое совпадение сборок не заявляется.
При подготовке JDK скачивается точный архив Temurin 21.0.12.1+1 с проверкой
SHA-256: `setup-java` не разбирает такой четырёхчастный номер. Локальная сборка
проходит; первый успешный облачный прогон ещё впереди. Его ZIP нужно отдельно
испытать с madVR.

## Обновление MPC-BE

`origin` предназначен для нашего форка, `upstream` — для оригинального MPC-BE.
Сохраняйте историю оригинала и вливайте выбранный официальный релизный тег в
ветку `update/`, например `update/mpc-be-1.9.2` при переходе на этот выпуск.
Не сливайте новые версии и не меняйте основу автоматически без локальной проверки
воспроизведения. Не заменяйте репозиторий снимком файлов оригинала. Обновите
подмодули до ревизий этого тега, разрешите изменения интеграции, обновите
`bluray/versions.json` и обе версии истории изменений.

Проверьте ресурсы версии, имя пакета и `update_revision.cmd`. Этот скрипт
намеренно выбирает числовые теги оригинала, исключая теги форка с дефисом,
чтобы они не ломали разбор номера ревизии. Выполните локальные тесты и живую
проверку, проверьте PR, затем влейте готовое изменение в `main`. До создания
тега публичного выпуска соберите и проверьте облачный кандидат.

## Обновление libbluray

Используйте отдельную ветку `update/libbluray-<версия>` и проверяемый PR,
с тем же порядком локальной работы, что и при обновлении MPC-BE.

[Два локальных патча](../../bluray/patches/README.md) снабжены исходными/конечными
хешами и регрессионными тестами. Они не отправлены и не приняты в оригинальный
проект. Перед обновлением проверьте, исправлена ли исходная причина разработчиками.
Удалять патч можно после прохождения его теста без патча; иначе осознанно
перенесите исправление на новые исходники и проверьте поведение.

Обновите архив и хеш исходников, манифесты патчей, заголовки API и версионные
пути/имена в скриптах, списке упаковки и Java-интеграции. Найти привязки к версии
поможет `rg '1\.5\.0' bluray include/libbluray src/apps/mplayerc`.
Пересоберите DLL и оба JAR вместе, выполните тесты патчей/HAVi/компонентов,
затем проверьте HDMV и BD-J в плеере. При необходимости обновите лицензии
и закреплённые зависимости. Не применяйте `--export` патча только ради обхода
неожиданного несовпадения хешей.

## Публикация и личные данные

Локальный pre-push hook запускает `check-public-tree.py`, если включён указанной
выше настройкой Git. Проверяются новые рабочие файлы и содержимое новых коммитов,
включая удалённое последующими коммитами. Скрипт ищет типичные секреты, личные
пути и лишние артефакты; он не доказывает обезличенность любого текста.

Перед push проверьте новые коммиты, имя и почту автора. Используйте выбранную
публичную идентичность, например адрес GitHub noreply. Не включайте профили,
журналы, снимки, файлы дисков, Java runtime, личные сохранения и пути компьютера.
Сведения об авторах оригинальных проектов и лицензии сохраняются.

Перед первым выпуском закончите подпись версии и документацию в ZIP, проверьте
всю отправляемую историю, выполните облачную сборку и испытайте её ZIP. Публикуйте
проверенный пакет с контрольной суммой и соответствующим тегом исходников как
предварительный выпуск. Русские и английские инструкции и история изменений
должны обновляться вместе.
